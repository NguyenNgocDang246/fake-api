# src/app — Agent Guide

## Summary

Everything Next.js routes: the API route handlers under `api/**`, and the UI. The UI is a thin presentation layer over React Query and react-hook-form; anything that decides something lives in `src/server/` or `src/models/`, so a rule is never enforced only in a component.

## Content

- `api/**` — route handlers. Composed from the `src/server/core/route_helpers.ts` chain (`createRouteHandler` or `createStaticRouteHandler`, then `withUserId`/`withProjectId`/`withEndpointGroupId`/`withEndpointId`), with the permission check inside the innermost handler. `api/fake/[projectId]/` is the public one that serves a user's mock endpoints. Nothing links to it: a mock is called as `{projectId}.{DOMAIN}/{path}` and `src/server/middlewares/fake.middleware.ts` rewrites onto it, putting the id on the dynamic segment where the handler reads it, while the mock path stays on `req.nextUrl.pathname` exactly as the caller wrote it. Called directly on any other host it is a 404 from that same middleware. The handler decodes the mock path one segment at a time, so an encoded `/` stays inside its segment, drops a trailing slash, and on a 3xx drops a `Location` that leaves the mock's own host. It refuses a path longer than `MAX_MOCK_PATH_LENGTH` before any lookup, that being the one thing worth keeping from the path validation a mock path cannot pass: a dynamic segment carries a value the author never wrote, so the arriving path is capped well above `MAX_PATH_LENGTH`, which caps the stored template it matches against.
- `(pages)/**` — the routed UI, grouped per page. A page owns a `page.tsx`, a `viewmodel.ts` and a `components/` folder. `(pages)/(marketing)/**` holds the search-facing landing pages, which are prose plus the `components/Marketing/**` kit and have no viewmodel. Every one of them does the same job, which is to teach a subject that stands on its own, and `faq/` answers across them. None is a sales page. The knowledge is what earns the keyword and the reader, so the product does not appear in the prose, the headings or the card grid at all: its one place is a row in that page's comparison table, sitting among the alternatives on the same axes, plus the call to action at the foot. `free-api-for-testing/` is the one page whose table does not hold that row, because its rows are the third-party datasets a reader picks between and every one of them links out, so the product is named in a closing section instead. A section that describes a feature belongs in `docs/`, not here. Their URLs are flat, with no `/blog` prefix, and each owns both a keyword cluster and a subject nothing else on the site targets, so a heading is never reused across two of them. They fall in two groups. The mock group is for a reader choosing how to mock: `mock-data/` takes where a mock belongs and which values are worth testing against, `mock-api-tools/` the dedicated mock services and whether a mock needs state at all, and `free-api-for-testing/` the public datasets a reader might use instead. The bug group is for a reader losing hours to a failure they cannot reproduce on demand: `cors-error/` takes the browser refusing to hand a cross-origin response to script, `race-condition/` the response that arrives after a newer one and wins the render, and `api-error-handling/` the six or seven distinct failures that a single error component collapses into one. All of them land on the same product with the same call to action, and they reach a reader through the header's Guides menu (`components/Wrapper/Header/GuidesMenu.tsx`, which holds the one list of them) under labels that say the job rather than repeat the keyword. The footer carries only `docs/` and `faq/`, the two a reader goes looking for by name. A URL is named for what the page teaches, not for the feature it sells.
- `(home)/**` — the landing page, plus `components/GuestPlayground/`, the client island where a visitor with no account builds and calls up to `ROLE_LIMITS.GUEST.maxEndpointsPerGroup` endpoints. It reuses the project page's endpoint components as they are and remembers which sandbox belongs to this browser in `localStorage` under `GUEST_SANDBOX_STORAGE_KEY`, because a visitor has no session to hang it on. The page renders it only when nobody is signed in.
- `components/**` — the shared UI kit: inputs (`DefaultInput`, `ComboInput` for a searchable dropdown that optionally creates values, `Checkbox`, `Switch`, `JsonEditor`), `Input/RepeatableRowList` for an add/remove row list (the response-header and CORS-origin editors), `Tabs/PillTabs` for a tab strip, either as pills sized to their labels (the preview switcher) or, in its `card` variant, as tabs sharing the full width evenly; `Tabs/FormTabs` for a whole tabbed form section, always on the `card` strip: it takes one entry per tab (`label`, `hasError`, `marked`, an optional `title`/`description`, and the `content` the caller builds) and owns the strip, the dots, keeping every panel mounted, and moving to the first broken tab on a failed submit, `Code/CodeBlock` for a fenced snippet, `Decor/HeroGlow` for the blurred background wash behind a hero, `Text/EmptyState` for the "nothing here yet" block (title, optional description, and a button the caller supplies, so it stays free of any one page's action), `Notify`, `JsonLd` for a structured-data script, `Marketing/**` (`MarketingHero`, `FeatureGrid`, `StepsRow`, `CtaBanner`, and `ComparisonTable` for a table that scrolls inside its own `overflow-x-auto` box rather than widening the page) for the blocks the home and landing pages share, the modal wrapper with its `ModalSize` scale, the React Query wrapper and its `QUERY_KEY`/`STALETIME` constants. `Wrapper/Consent/**` is the analytics gate: `ConsentWrapper` holds the answer and the `useConsent` hook, `Analytics` renders `GoogleAnalytics` once that answer is `granted`, `CookieBanner` asks while it is unanswered, and `CookiePreferencesButton` is the footer control that clears it to ask again. `Wrapper/Header/**` holds the site header: `HeaderWrapper` picks `GuestHeader` or `UserHeader` off `useAuth`, and both take their nav from `HeaderNav`, which is the one place the width at which that nav folds is written. Below `sm` it renders the same destinations as a single menu button instead of a row, so a header change is made once and the two variants keep only what actually differs between them, the Login button and the account menu.
- `(pages)/privacy/` and `(pages)/terms/` — the two legal pages, prose with no viewmodel and no marketing kit. They sit outside `(marketing)` because that group is for keyword pages that teach a subject, which these are not. Both are noindex and absent from the sitemap, and both are reached from the footer. Figures in their copy come from `ROLE_LIMITS`, the `endpoint/primitives.model` limits and `guest.constants`, never retyped.
- `styles/globals.css` — the only stylesheet: the Tailwind v4 entry, the `--scroll-*` and toast tokens, the global scrollbar treatment, and the `react-toastify` skin.
- `libs/helpers/**` — pure helpers shared by both halves of the app. See [libs/helpers/AGENTS.md](libs/helpers/AGENTS.md).
- `libs/routes.ts` — `API_ROUTES` and `PAGE_ROUTES`, the one place a URL template is written.
- `libs/seo.ts` — `SITE` (name, absolute URL, description), `absoluteUrl`, `buildMetadata`, which every page calls instead of writing a `Metadata` object by hand, and `breadcrumbSchema`, which turns the page's `Crumb[]` into its `BreadcrumbList`.
- `robots.ts`, `sitemap.ts`, `manifest.ts`, `opengraph-image.tsx`, `twitter-image.tsx`, `icon.png`, `apple-icon.png` — Next file conventions for the crawler-facing and share-facing assets.
- `llms.txt/route.ts` — the llmstxt.org index an AI assistant reads instead of crawling: the site description, the shape of a mock URL, then a link list covering `docs/`, the guides and `faq/`, with `privacy/` and `terms/` under the standard `Optional` heading that a reader short on context may skip. It is a route handler rather than a file in `public/` so its links come from `PAGE_ROUTES` and `SITE.url` like the sitemap's do, and `force-static` prerenders it at build.

## Conventions

- **A component folder is `ComponentName/ComponentName.tsx` plus a `viewmodel.ts`.** The `.tsx` renders; the viewmodel is a hook holding the React Query state, the mutations and the modal opening. A `*Skeleton.tsx` sits beside them when the list has a loading state. Files here are `PascalCase` for components and lowercase for the rest, which is the one place the repo's `snake_case` file rule does not apply.
- **An endpoint is one address and a list of scenarios, and a column beside the form is how it moves between them.** `method` and `path` sit above the two columns; the status, body, headers, delay and AI panel all live inside a page and every field name carries its index, `scenarios.${i}.…`. `ScenarioList` is the left column, a row per scenario carrying its own name, status code, delay and whether it is the one answering, so an author reads the set without opening each one. `ScenarioHeader` is the top of the page itself, where that name is typed and where the answering scenario is chosen or the page deleted. Green marks the row the mock answers with and blue the row on screen, which are two different things the moment an author opens a page without switching to it, and red takes both when that page cannot be submitted. Every page stays mounted and the ones off screen are hidden, for the same reason `FormTabs` does, and a failed submit opens the first broken page before `FormTabs` opens the tab inside it. `maxScenarios` of 1 hides the column and the header entirely, which is what the home page's trial box passes.
- **The endpoint list ships one scenario and a count of the rest.** A row only ever draws the one that is answering, so `GET_ALL` sends that alone beside `scenario_count`, which is a subquery rather than a second read of the bodies. Everything that needs the others asks `GET_BY_ID`: `UpdateEndpointForm` when it opens, standing an `EndpointFormSkeleton` in until they arrive, and `ScenarioSwitcher`, the menu on the row itself, once somebody opens it. `EndpointItem` warms that same answer on a settled hover, and all three go through the one `endpointByIdQuery`, so an open that follows the pointer waits for nothing. Mounting `useForm` on the real values rather than resetting into them is what keeps `JsonEditor`, which measures itself once, from being left at the wrong height.
- **Which scenario answers can be changed from the row, without opening the form.** `ScenarioSwitcher` posts `SCENARIO_ACTIVATE`, the one route that does only that, and the answer is the whole endpoint, so the row and the modal are both written from it instead of refetching a list that already knows what changed. It is offered on the count alone, so an endpoint holding one scenario has nothing there, and the home page's trial box offers it too: switching is the whole point of keeping a second saved response, and the guest prefix carries this one route past an endpoint id for it.
- **A form opens on what the cache holds, so whatever writes has to leave that key right.** `useForm` reads its defaults once, at mount, and a modal is built fresh every time it opens, so an endpoint the user has just saved is what `[QUERY_KEY.ENDPOINT.ONE, id]` must hold or the next open shows the values the save replaced, and no later refetch can move a form that has already mounted. Both routes that change an endpoint answer with the whole of it for this reason, and the caller writes that answer in with `setQueryData` and invalidates behind it, because a blueprint settles in an `after()` task past the response and only a refetch has it.
- **An endpoint component takes its project id and its route templates as props.** `CreateEndpointForm`, `UpdateEndpointForm` and `EndpointItem` all default to the project page's behaviour (project id read off the pathname, `API_ROUTES.ENDPOINT`), and the home page's trial box passes `projectId`, `endpointRoutes: API_ROUTES.GUEST.ENDPOINT` and `aiAvailable: false` instead. It has to be props and not context: a modal's children are created in the caller's scope but rendered under `ModalWrapper` near the root, and context resolves where a node renders. `EndpointForm` unmounts the AI panel rather than hiding it when `aiAvailable` is false, because that section fetches its own status and quota.
- **A form is driven by its modal, through a ref.** The form is a `forwardRef` exposing `useImperativeHandle(ref, () => ({ submit }))` where `submit` resolves `true` or `false`, and the viewmodel holds the `formRef` and passes `onSubmit` to `modal.openModal({ type: "form", ... })`. The modal decides whether to close; the form never does.
- **A `customResolver` checks by hand first, then delegates to `zodResolver`.** Coercions and the checks Zod cannot phrase run first and short-circuit; everything else is the shared schema's job. The schema in `src/models/**` is the single source of every limit and every message, so a form must never restate a rule it could import. Where the browser can prevent a value outright (`maxLength` on an input), do that too, but the resolver still decides.
- **A rule the server enforces is mirrored, never re-implemented.** `validateAiFields` wraps the same `checkAiFieldSelection` the Zod schema calls, so the message a user sees before the request and the one that would come back are the same string. Two copies of a rule drift, and the drift shows up as the form and the API disagreeing about the same input.
- **A create form and its update twin share one body.** `EndpointForm` is that body for endpoints and `ProjectForm` for projects: the wrapper owns the mutation and the `useForm`, and passes `register`/`control`/`errors`/`setValue`/`submitCount` down. Both halves validate by the same schema, since `ClientUpdateProjectSchema` *is* `ClientCreateProjectSchema` (as `ClientUpdateEndpointByIdSchema` is `ClientCreateEndpointSchema`), so an update can never accept something a create refuses.
- **A repeated row keeps the index the form rendered it at.** `ResponseHeadersEditor` and the origin list in `ProjectForm` both let a user add a row and leave it empty, and both are validated by a Zod `superRefine` that skips a blank row and reports every other issue at the index it was handed, with the blank rows dropped by a transform that runs afterwards. Filtering before validating would shift an error onto the wrong row, which is the one thing a per-row message must not do.
- **A tabbed form keeps every panel mounted** and hides the inactive one, and a failed submit opens the panel carrying the first error. `JsonEditor` measures its own height once on mount and holds its undo stack in a ref, so remounting a panel throws away a half-typed body, and an error message under a hidden control is one nobody reads. `Tabs/FormTabs` is where both of those live, so `EndpointForm` and `ProjectForm` describe their tabs and nothing else. What goes *inside* a tab is not shared: the AI variants card and the project's CORS card look alike but each stays its own markup, because a panel is where a feature's design belongs.
- **`JsonEditor` is two layers that have to read as one.** A textarea whose own text is transparent sits over a `pre` holding that text in colour: the caret, the selection and the typing are the textarea's, everything anybody reads is the overlay's. So the two agree to the pixel on font, tab stops, padding and border, and a line long enough to scroll sideways scrolls both, or the caret ends up beside the character it is on rather than on it. A body is read by its indentation, so a long line runs off the side and is scrolled to rather than folded into the line below, and the box that fits itself to its content leaves room for the scrollbar that line puts inside it.
- **A block that changes shape inside a modal measures its own container, not the viewport.** The AI section and the settings grid use `@container` with px breakpoints, because a `sm:` breakpoint says nothing about how much room a `w-[44rem]` panel actually left them. Write those breakpoints in px: `html` is 18px here, so `rem` inside a container query resolves to more than it reads as.
- **An empty list that a user can fill offers the way to fill it.** Those places use `EmptyState` with a title, a line saying what the thing is for, and the create button, rather than a bare "No X found". A list that is empty because of a filter is not this: it stays a plain `NoContentText`, since there is nothing to create. Neither is a list whose create button is already right beside it, such as the endpoint-group sidebar.
- **The UI never reports what it cannot know.** While the JSON body will not parse, the field selector says nothing about which fields exist rather than listing all of them as missing. The server side of this feature answers the same way, reporting `undefined` rather than a stale verdict.
- **Server state goes through TanStack Query**, keyed by `QUERY_KEY` and aged by `STALETIME`, and a mutation invalidates the key it touched. Answers fixed at boot are seeded with `queryClient.setQueryData` from the server component instead of being fetched. `QUERY_KEY.USER.USAGE` is the one query that opts out of `STALETIME` and runs at `staleTime: 0`: saving an endpoint can spend an AI design in an `after()` task that finishes past the response, so no invalidation can be timed against it and opening the AI card is the moment to ask again. Where a response already knows the new count, as the AI preview route's does on both its answer and its refusal, the viewmodel writes it in with `setQueryData` rather than paying for a refetch.
- **Scrollbars come from one global rule in `globals.css`.** Every scrolling element is thin and trackless, with the thumb fading in only while that element is hovered or focused within, driven by the `--scroll-*` tokens. A dark-backgrounded scroll box carries `fa-scroll--dark` (or `fa-code` / `fa-json` for a code or JSON `pre`) so its thumb stays visible; `fa-scroll` and its `--always` / `--fade` / `--fade-bottom` modifiers are the opt-in helpers. A component never restyles its own scrollbar.
- **User-facing strings are English.** Comments too.
- **A page declares its metadata through `buildMetadata`.** It fills in the canonical URL, the Open Graph block and the Twitter card from one title, description and `PAGE_ROUTES` path, so no page hand-writes a canonical or restates the site name. It names the share image explicitly, because a page that declares its own `openGraph` block stops inheriting the root `opengraph-image` file convention.
- **Thin pages are excluded with a noindex tag, never with a robots.txt disallow.** A blocked crawler never reads the tag, so the URL can still surface as a bare link. `(pages)/auth/layout.tsx` carries the one `robots: { index: false }` that covers every auth page.
- **Structured data is rendered from the same array the page renders.** The FAQ page maps one `FAQ` constant into both the visible list and the `FAQPage` schema, because Google treats a schema answer that is not on the page as a violation. The same holds for the trail: a page declares one `BREADCRUMB` array, passes it to `Breadcrumb` for the visible nav and to `breadcrumbSchema` for the `BreadcrumbList`. Figures quoted in that copy come from the shared constants (`ROLE_LIMITS`, the `endpoint/primitives.model` limits), never retyped.
- **A landing page splits its description in two.** `META_DESCRIPTION` feeds `buildMetadata` and the page's schema and measures 150 to 160 characters; `HERO_DESCRIPTION` is the longer line under the `<h1>`. One string cannot serve both, because the search snippet gets cut and the hero reads clipped. Both bounds bite: under 150 an auditor reports the description as too thin to earn the snippet, and past 160 Google truncates it. `SITE.description` sits in the same band, since it is what `/` serves.
- **`/` takes its title from the root layout's `title.default`, not from its own `metadata`.** The default is the bare site name, and the template `%s | Fake API` would turn a page-level title into "Fake API | Fake API". That layout is also the one place `openGraph` is declared without `buildMetadata`, so it names the `images` array by hand for the same reason `buildMetadata` does.
- **Analytics is mounted once by the root layout and only behind consent.** `Analytics` renders nothing unless `NEXT_PUBLIC_GA_ID` is set and `useConsent` reads `granted`, so a missing id and a refusal both end in no request to Google, and GA4 Consent Mode is deliberately not used because it would still ping on a refusal. `GA_ID` is read once in `Analytics.tsx` and every piece of the gate imports it from there, including the banner and the footer control, which render nothing without it: a build with no id must not ask anyone for permission it cannot use. Withdrawing an accepted consent drops the `_ga` cookies and reloads, since a gtag already on the page cannot be unloaded, and a `storage` listener carries that withdrawal into the other open tabs. Those cookies are also swept on any load without consent, because a tab whose gtag is still alive rewrites them in the gap before it reloads and that race cannot be won. Page views on a client-side navigation come from GA4's Enhanced measurement setting, not from any code here, so turning that setting off in the GA console silently reduces the site to one event per full page load. An event is reported through `useAnalyticsEvent` and never through `sendGAEvent` directly: without consent gtag was never initialised, and the library's own call warns into the console of the visitor who asked not to be measured.
- **An event that belongs to one caller is passed in as a prop.** `guest_endpoint_created` is the trial box's conversion, and `CreateEndpointForm` serves the project page too, so the form takes an `onCreated` callback rather than reporting the event itself. A shared component that fires its own analytics reports for every caller it will ever have.
- **An outbound link goes through `TextLink` with `external`.** It swaps `next/link` for an `<a>` carrying `target="_blank"` and `rel="noopener noreferrer"`, which is the pairing `NavigationButton` already applies. A raw `<a>` in a page misses the `rel` and hands the opened tab a `window.opener` reference.
- **`HeroGlow` is rendered once, by the root layout, and never by a page.** It is anchored to `body`, which carries `relative` for it, so every page sits on the same wash and no page has to remember to add one. The glow is sized to spill past its ancestor, which is how it reaches the viewport edges and fills the gap under the sticky header. It contains its own horizontal bleed with `overflow-x-clip` on its container: that container is `inset-x-0`, so the cut lands exactly on the viewport edges where nobody can see it. Do not rely on the `overflow-x-clip` that `body` also carries. `body`'s overflow is propagated to the viewport and `body` itself falls back to `visible`, so it clips nothing, and a child wide enough to overflow will make the whole document scroll sideways. `clip` is still the right value on both, since unlike `hidden` it does not create a scroll container and so leaves the sticky header working.
- **The `<h1>` carries the page's target phrase verbatim.** `/mock-data` says "mock data" and `/mock-api-tools` says "mock API tools" inside the heading itself, not only in the badge above it.
- **A landing page hero carries no buttons.** `MarketingHero` takes `primaryHref` and `secondaryHref` optionally and renders the pair only when the first is given, which is `faq/` alone. A reader arriving on a keyword page has not been told anything yet, so the only call to action is the `CtaBanner` at the foot, after the page has earned it.
- **A bug-group page teaches the failure, not this codebase's handling of it.** Its facts come from the specification and from what a browser actually does, so every sentence holds for a reader who never signs up. `src/server/core/cors.ts` is not a source for `cors-error/`: writing the page from the implementation is how a landing page turns into product documentation with a keyword on it. What the product offers such a reader is a way to reproduce the failure, so that is the axis its table compares, and the table is about reproducing rather than about fixing.
- **The pill badge belongs to `MarketingHero`, and to nothing else.** It is the tag a landing page wears above its `<h1>`, and it reads as one because no other section on the site carries it. A section that wants more weight gets it from the blocks the theme already has, the `indigo-600` to `blue-500` gradient among them, not from a second badge.
