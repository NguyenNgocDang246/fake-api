# src/server/services/endpoint — Agent Guide

## Summary

Everything about a stored endpoint: its CRUD, how an incoming fake-API request is resolved to one, and the pool of AI generated response variants an endpoint can serve instead of its static body. A folder rather than a single file because the variant pool has its own lifecycle, its own prompt, and its own quota, none of which the CRUD layer needs to know about.

`endpoint_group.service.ts` stays outside this folder: a group is its own domain, and it owns the endpoints rather than being part of one.

## Content

- `endpoint.constants.ts` — `ENDPOINT_MESSAGES`, plus the three groups of variant tuning constants: pool sizing and the refill lock (`AI_POOL_SIZE`, `AI_POOL_LOW_WATER`, `AI_VARIANT_MAX_USES`, `AI_REFILL_LOCK_MS`), the prompt context caps (`AI_CONTEXT_*`), and the output token budget (`AI_MAX_OUTPUT_TOKENS`, `AI_TOKENS_PER_VALUE`, `AI_MIN_OUTPUT_TOKENS`, `AI_THINKING_RESERVE`). They keep the `AI_` prefix but belong here, not in `../ai/`, because every one of them describes this feature's pool and prompt rather than the LLM layer. What each trades off is in the conventions below.
- `endpoint.service.ts` — CRUD scoped to a user/project, plus the role-limit check before create. It also resolves incoming fake-API requests to a stored row: `getEndpointByPath` is an exact literal match (tried first, from `src/app/api/fake/[projectId]/route.ts`); `getEndpointByDynamicPath` is the fallback, matching `:paramName` segments in `path` (e.g. `/user/:id`) via the pure `matchPathTemplate(template, pathname)` helper. Static match always wins, dynamic is only attempted when the exact lookup returns nothing. `findMethodsForPath` is the third and last step, asked only when both have missed: it ignores the method and reports which verbs the project does serve at that path, which is what lets the fake API answer 405 instead of 404.
- `endpoint_variant.service.ts` — lifecycle of one endpoint's variant pool: `pickVariant` (the least used row, so the pool is walked in order rather than sampled), `markVariantUsed`, `needsRefill`, `refillIfNeeded`, `clearVariants`, `prunePool`, and the per-role daily quota in `canGenerate`/`canRefill`.
- `endpoint_variant_generator.service.ts` — the bridge to `../ai/`. Shrinks the body into prompt context, extracts the current value of every allowed path, validates each patch the model returns, and applies it to a clone of the base body.
- `endpoint_variant_prompt.ts` — the system prompt, the context block, the user message, and the structured-output schema. Kept apart from the generator so the wording can be tuned without touching path extraction or patch validation.

The split between the last two and `../ai/` is deliberate: `ai/` knows nothing about endpoints, so a future chatbox can reuse it as is. Everything endpoint-specific (prompt text, path extraction, patch validation) lives here.

## Conventions

- **The model never returns a whole body.** It only returns `path -> new value` pairs for the fields the user allowed, and the server clones the base body and overwrites exactly those paths. A field that was not allowed is structurally incapable of changing, however badly the model misbehaves.
- **The wrong verb on a real path is a 405, and it costs the healthy path nothing.** Both resolvers filter by `method`, so a wrong-verb request misses them and used to fall out as a 404, which is the one answer that is not true. The extra `findMethodsForPath` lookup runs only after both have missed, and the allowed verbs come back in the error payload. Anything that adds a fourth resolution step has to keep that ordering, or every request starts paying for the miss path.
- **Serving a fake request only reads.** `pickVariant` is a single row read; counting the use and refilling are deferred to `after()` so an AI-enabled endpoint is no slower than a static one. `refillIfNeeded` therefore never throws: the response has already been sent, and a failed refill only means the next request serves the base body.
- **A use is counted for a variant that was actually served.** The fake route parses the stored row before scheduling the `after()` callback, so a row whose JSON is corrupt falls back to the base body without spending one of its `AI_VARIANT_MAX_USES`. Scheduling first meant such a row was counted for a response nobody received and then sat in the pool until it happened to wear out. The refill still runs, since a corrupt row is exactly what needs replacing.
- **A variant pool rotates, it does not grow.** Both the refill trigger (`needsRefill`) and the batch size are measured on `countUsableVariants`, rows still under `AI_VARIANT_MAX_USES`, never on the raw row count, or a full pool of worn out rows would look stocked. The replacements are generated first and `prunePool` drops the worn tail after, so the pool never dips to empty while the model is running and an endpoint stays capped at `AI_POOL_SIZE` rows for good.
- **`endpoints.ai_refill_started_at` is both the refill lock and the retry cooldown.** It is released deliberately, not in a `finally`: only a refill that stored rows, or one that found the pool already stocked, hands it back. A refill that produced nothing leaves it set so the next attempt waits out `AI_REFILL_LOCK_MS` instead of firing on the very next request. The timestamp is generated by the application, not `NOW()`, so both sides of the staleness comparison read the same clock, and the release carries it in its `WHERE` so a refill that outran the lock cannot clear its successor's.
- **An edit ends the cooldown, so `clearVariants` drops the lock too.** The cooldown exists to stop a dead provider being hammered, and an edit is exactly the signal that the inputs changed. Without this a refill that failed on a broken body kept the endpoint frozen for `AI_REFILL_LOCK_MS`, so the user fixed the body and the server went on quietly serving the base body for another three minutes.
- **A refill re-checks that it still owns its lock before it writes.** A model call takes seconds and an edit can land in the middle of one: `clearVariants` wipes the pool and drops the lock, and the refill still in flight would otherwise insert variants built from a body that no longer exists, which nothing would ever clean up. `generateAndStore` takes the lock token and discards its own output when the token no longer matches.
- **The lock is written with `$executeRaw`, on purpose.** `endpoints.updated_at` carries `@updatedAt`, so touching `ai_refill_started_at` through Prisma would bump it and reorder the `updated_at desc` candidate list that `getEndpointByDynamicPath` uses to break ties between path templates. Raw SQL keeps the lock invisible to that ordering. It is a tagged template, so the values are still parameterized.
- **`refillIfNeeded` answers "may this endpoint spend tokens" in full, before it takes the lock.** `ai_enabled`, a non-empty field list and `isAiConfigured()` are all checked in the same place and ahead of everything else. The configuration check belongs there rather than at the call sites for the same reason the other two do, and ahead of the lock because a server with no keys reaches no vendor: without it every request to an AI endpoint counted the pool, *wrote* the lock, counted again, resolved the owner for the quota, and only then let `chat` throw `NOT_CONFIGURED` into the log, repeating per endpoint every `AI_REFILL_LOCK_MS`. `ai-preview` already guarded itself this way.
- **Every path that spends tokens is quota checked.** `POST .../endpoint/ai-preview`, the one route a user clicks straight through to a model, calls `canGenerate`; the automatic refill calls `canRefill`, which resolves the owning user from the endpoint id and applies the same per-role daily limit. Any new route that reaches the generator has to pick one of the two.
- **A field the generator cannot patch is refused before the call, not discovered by the vendor.** `buildVariantJsonSchema` describes a value by its JSON type and has a schema for the four leaf types only, so a path pointing at an object or a nested array leaves that property as `{}`. Providers reject a structured-output schema like that, and the router treats a refused payload as fatal, so one such path costs a paid call and answers 500 about our own request being malformed. Two layers stop it: `checkAiFieldList` in `@/models/endpoint.model` rejects the selection at the route with a 400 naming the field, and `buildEditableFields` drops the path regardless of which caller asked. The schema check is shared by create, update and preview, so a selection previews exactly when it saves.
- **A `[]` path describes one element type, so the whole array has to agree on it.** `buildVariantJsonSchema` gives an array path a single `items` schema and `validateVariantPatch` checks the reply element by element, so a ragged array (`[{price: 1}, {price: "2"}]`, or an element missing the key) describes a field no reply can satisfy. `uniformElementType` here drops such a path, but that alone was a silent failure: `buildFieldTree` typed an array from `elements[0]`, so the path was offered, ticked and saved, and every refill then dropped it and retried on the next `AI_REFILL_LOCK_MS` without ever storing a variant. The rule now lives in `buildFieldTree` (`@/app/libs/helpers/json_path`), which greys the checkbox, keeps the path out of `collectSelectablePaths`, and so makes `checkAiFieldList` answer 400 naming the field. `uniformElementType` stays as the backstop. Both sides cap the elements they inspect at `MAX_AI_ARRAY_ITEMS`, since only those are ever regenerated, and both count `null` as its own type, or one side would accept what the other drops.
- **A field list that is empty and one that was emptied are different failures.** `generateVariants` answers `NO_FIELDS_SELECTED` only when nothing was selected; a list that arrived non-empty and lost every path to `buildEditableFields` answers `FIELDS_NOT_PATCHABLE`. They shared a message, so a user who had ticked several boxes and then edited the body out from under them was told to tick at least one.
- **A wide selection buys fewer variants per call, and the refill cadence follows.** `planBatch` sizes the batch from the output token budget, so a selection near the `MAX_AI_VALUES` ceiling affords one variant per call rather than a full pool. `refillIfNeeded` hands the lock back as soon as a row is stored, so the next request refills again until the pool reaches `AI_POOL_LOW_WATER`, which at the top of that range works out near one model call for every two fake-API requests. That is the design working, not a runaway: the daily quota and the process rate limit are the ceilings, and `MAX_AI_VALUES` is what keeps the worst case reachable only for a deliberately huge selection. Anything that makes the batch smaller makes this cadence faster, so change the two together.
- **Thinking is billed against the output budget, so `planBatch` reserves a share of it.** Both adapters run with thinking on and those tokens count towards `max_tokens`/`maxOutputTokens` like any other output. The budget used to be the JSON size estimate exactly, which meant it shrank in step with the selection and the thinking-to-JSON ratio never changed: `AI_MIN_OUTPUT_TOKENS` rescued the small end, and the wide end had no headroom at all and truncated. `planBatch` now fits the JSON into `AI_MAX_OUTPUT_TOKENS * (1 - AI_THINKING_RESERVE)` and requests the estimate divided by `1 - AI_THINKING_RESERVE`. Lowering `MAX_AI_VALUES` is not a substitute, for exactly the reason above, and `MAX_AI_VALUES` is instead derived from that JSON budget, so the two move together or a selection saves and then fails on every call.
- **The scaffolding is charged once per reply, not once per variant.** `BATCH_TOKEN_OVERHEAD` comes off the budget before `planBatch` divides by the per-variant cost. Folding it into the divisor made a batch look more expensive than it is, and since `AI_POOL_SIZE` is ten, a three field endpoint that could not reach ten variants in one call paid for two.
- **`endpoint_ai_variants` has no `public_id`**, the one exception to the project-wide ID rule. It is an internal cache that never appears in a URL or an API response, and a whole pool is written with a single `createMany`, which `createWithUniquePublicId` cannot do.
- **The pool is invalidated by the routes, not by this folder.** Changing an endpoint's body, field list, or hint makes every stored variant stale, so `PUT .../endpoint/[endpointId]` compares the old row against the new one and calls `clearVariants` in `after()`. Any new write path that touches those three columns has to do the same. Field lists are compared as sets, since order carries no meaning and reordering a checkbox must not throw away a pool that is still valid.
- **Switching AI on seeds the pool, on create and on update alike.** POST schedules a refill for every new endpoint; PUT schedules one when `ai_enabled` goes from false to true, even though nothing went stale. Without that second case the endpoint served its base body until some unrelated edit happened to trigger a refill.

Error handling, list ordering, and other conventions shared with the sibling services are in [../AGENTS.md](../AGENTS.md).
