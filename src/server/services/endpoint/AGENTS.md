# src/server/services/endpoint — Agent Guide

## Summary

Everything about a stored endpoint: its CRUD, the scenarios that hold its answers, and how an incoming fake-API request is resolved to one. An endpoint owns only what addresses it, `method` and `path`; the status, body, headers, delay and AI settings all belong to whichever of its scenarios is active. The blueprint that lets an endpoint answer with different data on every call lives one level down, in [variant/](variant/AGENTS.md), because it has its own lifecycle, its own prompt, its own executor and its own quota, none of which the CRUD layer needs to know about.

`endpoint_group.service.ts` stays outside this folder: a group is its own domain, and it owns the endpoints rather than being part of one.

## Content

- `endpoint.service.ts` — CRUD scoped to a user/project, plus the role-limit check before create. `createEndpoint` and `updateEndpointById` write the endpoint and reconcile its scenarios inside one transaction, and both are wrapped in `retryOnPublicIdConflict` because every id in that transaction is generated, not just the endpoint's. `getEndpointById` addresses a row by `public_id` alone and carries every scenario, since it is what the edit modal opens its pager on.
  It also resolves incoming fake-API requests. `getEndpointByPath` answers one question only, whether a path is already taken, and selects nothing but `public_id`: it is the duplicate check both write routes run. The serving path uses `getServableEndpointByPath` for an exact literal match, then `getServableEndpointByDynamicPath` as the fallback, matching `:paramName` segments in `path` (e.g. `/user/:id`). Static match always wins, dynamic is only attempted when the exact lookup returns nothing. `findMethodsForPath` is the third and last step, asked only when both have missed: it ignores the method and reports which verbs the project does serve at that path, which is what lets the fake API answer 405 instead of 404.
- `scenario.service.ts` — the saved answers of one endpoint. `reconcileScenarios` brings a stored endpoint in line with the array a form submitted, inside the caller's transaction, and returns the ids in the order they were sent so the caller can hand each its own blueprint envelope. `setActiveScenario` is the switch on its own, for an author changing which one answers without reopening the form. `canHoldScenarios` checks the array that arrived rather than counting rows, because the whole pager is written at once. `getScenarioInGroup` replaces the endpoint-level lookup the AI preview route used to make, for the same reason it existed: the blueprint now hangs off a scenario.
- `scenario_plan.ts` — what the two write routes need from the blueprint layer without knowing how it works: `countDesigns` across every scenario being saved, `readWriteBody` for the size guard, and `settleScenarioPlans`, the `after()` task that adopts, carries forward, clears and builds.
- `scenario_view.ts` — the two shapes a stored scenario is read into, one for the wire and one for the blueprint layer.
- `endpoint_path_match.ts` — the two pure helpers behind that fallback. `matchPathTemplate(template, pathname)` decides whether one template matches, and `compareTemplateSpecificity` decides between two that both do. Pure and dependency free, so they are tested without a database.
- `endpoint.constants.ts` — `ENDPOINT_MESSAGES`, `ENDPOINT_AI_MESSAGES` (what designing or serving a blueprint refuses with: an unusable selection, a body that is not an object, a preview payload too large, a blueprint that does not fit), plus the tuning `variant/` reads: the build lock `AI_PLAN_LOCK_MS`, the prompt context caps `AI_CONTEXT_*`, `AI_PREVIEW_MAX_REQUEST_BYTES` and `AI_PLAN_MAX_OUTPUT_TOKENS`. They keep the `AI_` subject but belong here, not in `../ai/`, because every one of them describes this feature rather than the LLM layer. `ENDPOINT_AI_MESSAGES` is here for exactly that reason: a message naming a response body or a field selection is domain knowledge, and `../ai/` may hold none.
- `variant/` — the blueprint an LLM designs once so faker can render a different response body on every request. See [variant/AGENTS.md](variant/AGENTS.md).

## Conventions

- **Two path templates that match the same request are ranked by specificity, never by row order.** `compareTemplateSpecificity` reads both left to right and the first segment where one is literal and the other is a parameter decides, so `/shop/list/:name` beats `/shop/:id/item` for `/shop/list/item`. Before this the winner was whichever row `updated_at desc` happened to put first, which is not a routing rule anyone chose: it came from the repo-wide default list ordering being reused in a lookup. Any write to either row, including a background blueprint build, could silently reroute a live request.
- **The stored `response_body` is the author's own text, byte for byte apart from whitespace.** `JsonSchema` proves it parses to an object inside the limits and then hands the original string back, and the fake route strips the whitespace outside its string literals rather than passing an object to `NextResponse.json`. `JSON.stringify(JSON.parse(x))` reorders integer-like keys, rounds an integer past 2^53, rewrites `10.00` as `10` and `\u0041` as `A`, and turns `1e999` into `null` and `-0` into `0`, none of which a mock whose whole job is a fixed response may do to it. Compacting is a text pass over the same bytes, so it costs none of that, and it is what makes an endpoint with a blueprint and one without answer in the same shape. A blueprint does not change the rule: `variant/json_source.ts` writes a rendered body back against the author's text, so only the paths the blueprint names are rebuilt and every other field keeps its own literal.
- **`response_headers` is JSON text, and the blocklist is enforced twice.** The column holds a serialized `{name, value}` array, like `response_body` and `ai_plan` rather than a JSONB column, which nothing here uses. Unlike `response_body` the exact bytes carry nothing, so the schema re-serializes on the way in and drops the rows an author left blank. `src/app/api/fake/[projectId]/route.ts` then filters `isBlockedHeader` again while serving: a row written before those rules existed never passed through them, and it must not be able to set a cookie the app's own domain would read. Reading is deliberately forgiving for the same reason, `parseResponseHeaders` answering with no headers rather than failing a request.
- **`MAX_ARRAY_ITEMS` is an invariant of the body, not a truncation point.** `JsonSchema` refuses a `response_body` holding a longer array, on every endpoint whether or not AI is on, so no field can be half varied and no length recipe can silently shorten a list. It only guards writes: `EndpointInfoSchema` reads without it, because rows stored before the rule must keep loading. That is also why every `getAtPath(…, MAX_ARRAY_ITEMS)` argument stays, since a grandfathered row is the one case where the cap still does real work.
- **At most one active scenario, never at least one, so the serving lookup orders rather than filters.** A partial unique index holds the ceiling, and a switch is two statements inside one transaction, deactivate then activate, because a single `UPDATE` setting both rows trips that index the moment the planner touches the new row first and a partial unique index cannot be deferred. Between those two statements an endpoint has none active, so `getServableEndpoint*` orders by `(is_active desc, position asc)` and takes one. Filtering on `is_active` would 404 a live mock for the length of that transaction.
- **Scenarios are ordered by `position`, not by `updated_at`.** That breaks the repo-wide list rule on purpose. `position` is rewritten dense from the array index on every save, so it is the order the author arranged, and a blueprint build running in the background writes to the same rows. Ordering by `updated_at` would let machine work reshuffle the pages under them, which is the same failure `compareTemplateSpecificity` exists to prevent one level up.
- **The dynamic-path lookup reads ids and paths first, then fetches only the winner.** Every `:`-carrying endpoint in the project is a candidate and all but one are thrown away, so a single query pulling whole rows would drag every candidate's body and blueprint across the wire. The specificity ranking happens on `{id, path}` alone, and the row that won is read once, with its serving scenario.
- **The list sends one scenario, the modal asks for the rest.** `getAllEndpoints` includes only the scenario that is answering, which is all a row's badges report. Ten endpoints with five scenarios each would be the whole group's bodies, up to `MAX_RESPONSE_BODY_CHARS` apiece, for a page that draws ten status badges. `getEndpointById` is what the edit form fetches, and it carries all of them.
- **A save counts every scenario that would reach a model, not one.** The quota refusal on both write routes has to be honest about the whole array, or a save carrying three designs passes on room for one and the other two answer with the base body forever without saying so. Only the active scenario is designed in `after()`; the rest build on their own first request, the way the fake route already handles a missing blueprint.

Error handling, list ordering, and other conventions shared with the sibling services are in [../AGENTS.md](../AGENTS.md).
