# src/server/services/endpoint — Agent Guide

## Summary

Everything about a stored endpoint: its CRUD, how an incoming fake-API request is resolved to one, and the pool of AI generated response variants an endpoint can serve instead of its static body. A folder rather than a single file because the variant pool has its own lifecycle, its own prompt, and its own quota, none of which the CRUD layer needs to know about.

`endpoint_group.service.ts` stays outside this folder: a group is its own domain, and it owns the endpoints rather than being part of one.

## Content

- `endpoint.service.ts` — CRUD scoped to a user/project, plus the role-limit check before create. It also resolves incoming fake-API requests to a stored row: `getEndpointByPath` is an exact literal match (tried first, from `src/app/api/fake/[projectId]/route.ts`); `getEndpointByDynamicPath` is the fallback, matching `:paramName` segments in `path` (e.g. `/user/:id`) via the pure `matchPathTemplate(template, pathname)` helper. Static match always wins, dynamic is only attempted when the exact lookup returns nothing.
- `endpoint_variant.service.ts` — lifecycle of one endpoint's variant pool: `pickVariant` (the least used row, so the pool is walked in order rather than sampled), `markVariantUsed`, `needsRefill`, `refillIfNeeded`, `clearVariants`, `prunePool`, and the per-role daily quota in `canGenerate`/`canRefill`.
- `endpoint_variant_generator.service.ts` — the bridge to `../ai/`. Shrinks the body into prompt context, extracts the current value of every allowed path, validates each patch the model returns, and applies it to a clone of the base body.
- `endpoint_variant_prompt.ts` — the system prompt, the context block, the user message, and the structured-output schema. Kept apart from the generator so the wording can be tuned without touching path extraction or patch validation.

The split between the last two and `../ai/` is deliberate: `ai/` knows nothing about endpoints, so a future chatbox can reuse it as is. Everything endpoint-specific (prompt text, path extraction, patch validation) lives here.

## Conventions

- **The model never returns a whole body.** It only returns `path -> new value` pairs for the fields the user allowed, and the server clones the base body and overwrites exactly those paths. A field that was not allowed is structurally incapable of changing, however badly the model misbehaves.
- **Serving a fake request only reads.** `pickVariant` is a single row read; counting the use and refilling are deferred to `after()` so an AI-enabled endpoint is no slower than a static one. `refillIfNeeded` therefore never throws: the response has already been sent, and a failed refill only means the next request serves the base body.
- **A variant pool rotates, it does not grow.** Both the refill trigger (`needsRefill`) and the batch size are measured on `countUsableVariants`, rows still under `AI_VARIANT_MAX_USES`, never on the raw row count, or a full pool of worn out rows would look stocked. The replacements are generated first and `prunePool` drops the worn tail after, so the pool never dips to empty while the model is running and an endpoint stays capped at `AI_POOL_SIZE` rows for good.
- **`endpoints.ai_refill_started_at` is both the refill lock and the retry cooldown.** It is released deliberately, not in a `finally`: only a refill that stored rows, or one that found the pool already stocked, hands it back. A refill that produced nothing leaves it set so the next attempt waits out `AI_REFILL_LOCK_MS` instead of firing on the very next request. The timestamp is generated by the application, not `NOW()`, so both sides of the staleness comparison read the same clock, and the release carries it in its `WHERE` so a refill that outran the lock cannot clear its successor's.
- **The lock is written with `$executeRaw`, on purpose.** `endpoints.updated_at` carries `@updatedAt`, so touching `ai_refill_started_at` through Prisma would bump it and reorder the `updated_at desc` candidate list that `getEndpointByDynamicPath` uses to break ties between path templates. Raw SQL keeps the lock invisible to that ordering. It is a tagged template, so the values are still parameterized.
- **Every path that spends tokens is quota checked.** The two routes a user clicks call `canGenerate`; the automatic refill calls `canRefill`, which resolves the owning user from the endpoint id and applies the same per-role daily limit.
- **`endpoint_ai_variants` has no `public_id`**, the one exception to the project-wide ID rule. It is an internal cache that never appears in a URL or an API response, and a whole pool is written with a single `createMany`, which `createWithUniquePublicId` cannot do.
- **The pool is invalidated by the routes, not by this folder.** Changing an endpoint's body, field list, or hint makes every stored variant stale, so `PUT .../endpoint/[endpointId]` compares the old row against the new one and calls `clearVariants` in `after()`. Any new write path that touches those three columns has to do the same.

Error handling, list ordering, and other conventions shared with the sibling services are in [../AGENTS.md](../AGENTS.md).
