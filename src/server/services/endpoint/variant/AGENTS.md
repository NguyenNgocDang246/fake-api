# src/server/services/endpoint/variant — Agent Guide

## Summary

The blueprint that lets one endpoint answer with different data on every call. A model designs the blueprint once per endpoint and never sees a request again; faker executes it inline on the serving path, so variety is unbounded and costs nothing per call. What used to be a stored pool of ten generated bodies is gone: `endpoint_ai_variants` was dropped, and with it the pool sizing, the use counter and the prune step.

A folder of its own, split from the CRUD in [../AGENTS.md](../AGENTS.md), because the blueprint has its own lifecycle, its own prompt, its own executor and its own quota, none of which endpoint CRUD needs to know about. The DSL itself (the Zod schemas, the entity and semantic catalogs, every cap) lives in `@/models/endpoint_plan`, not here, because the preview route accepts a blueprint from the client and so it is a DTO. `@/app/libs/helpers/plan_summary` turns one into the plain-language rows the UI shows.

The split from `../../ai/` is deliberate: `ai/` knows nothing about endpoints, so a future chatbox can reuse it as is.

## Content

### Lifecycle

- `plan.service.ts` — the entry point every caller imports, and the only stateful piece. `loadPlan`/`loadRenderable`/`isPlanStale` read a stored blueprint, `planForHash` reads one for a caller's own inputs rather than the stored ones, `planInfoOf` reports its verdict for the UI badges, `ensurePlan` runs the whole guarded build (lock, quota, build, store), `adoptPlan` stores a blueprint the client already holds, and the lock helpers plus `buildPlan`, `splitSelection` and `planHash` are re-exported from here so nothing else has to reach past it.
- `plan_hash.ts` — `planHash`, the identity of the inputs a blueprint was built from: the body normalized through a parse, the sorted field list, the trimmed hint.
- `plan_lock.ts` — the four raw-SQL writes against `endpoints`: `acquirePlanLock`, `releasePlanLock`, `holdsPlanLock`, `clearPlan`, plus `ownerOf` for the quota check.
- `plan_cache.ts` — process-local memo of the parsed blueprint and its derived data, keyed by `ai_plan_hash` and confirmed against the stored text. `parsePlan` is the never-throwing Zod pass; `resetPlanCache` exists only for tests.
- `plan_build.ts` — the model call. `splitSelection` separates value fields from array containers, `buildPlan` assembles the prompt, extracts the JSON, and runs the one repair attempt.
- `plan_catalogs.ts` — `collectUniqueCatalogs`, kept out of the executor so the serving path can compute it without pulling in faker.

### What the model is told

- `fields.ts` — what the model is told about the body. `buildContextBody` shrinks the body to fit a prompt without abbreviating any path the user selected; `buildEditableFields` extracts the type and current value of every path that holds a JSON leaf. The `EditableField` type lives here because this is where it is produced.
- `plan_system_prompt.ts` — the system prompt describing the whole DSL, built from the catalogs and caps in `@/models/endpoint_plan` so a name added there reaches the model without being retyped.
- `plan_prompt.ts` — the context block and the user message, plus a re-export of the system prompt. Kept apart from the service so the wording can be tuned without touching the lifecycle.

### Judging a blueprint

- `validate.ts` — `validatePlan`, which refuses a blueprint that does not agree with the body it would be applied to. Split from the executor because it needs no faker at all: the design service and every caller that only has to judge a plan imports this one and so never loads the locale datasets.
- `validate_recipe.ts` — the per-recipe shape and type checks behind it.
- `validate_types.ts` — the shared `Resolved`/`ValidateRecipeInput` types and the type resolution a recipe's output is judged against.
- `validate_graph.ts` — `scopeKeyOf`, `wholeArrayReads`, `validateScopes` and `validateAcyclic`: the checks that read the blueprint as a graph rather than field by field.

### Drawing the values

- `faker.service.ts` — the executor. `renderVariant` runs a blueprint against a base body and hands back a fresh value.
- `faker_context.ts` — the `RenderContext` and the caches on it: one entity draw and one catalog row per id per index path, and `readReferenced`, which resolves a dependency at the indices being drawn.
- `faker_recipe.ts` — `drawValue`/`drawUnique`, the switch from a recipe kind to a value.
- `faker_entity.ts` — one draw fills every attribute of an entity at once, which is where "the email belongs to the name" becomes a fact about the code.
- `faker_semantic.ts` — `drawSemantic`, a switch with no `default` over `SEMANTIC_TYPES`.
- `faker_value.ts` — the leaf-level helpers shared by the two above: number shaping, date formatting, weighted picks, pattern rendering.
- `faker_locale.ts` — the eight Faker instances, one static import per locale subpath. The only files in the repo that import `@faker-js/faker` are this one and the three above it.

## Conventions

- **The model designs, it never generates.** It returns a blueprint of `path -> recipe`, and the executor draws the values. This is what makes coherence a property of the code rather than a request in a prompt: an email is built from the first and last name of the same person draw, a total is summed from the line items that were just written. Anything that has the model produce values again gives that up.
- **A blueprint is untrusted twice over.** A model wrote it, and the preview route accepts one from the client. Nothing in it ever reaches faker through a dynamic string: every `kind`, entity attribute and semantic name resolves through a hand-written switch, so a name outside the whitelist cannot execute anything. That switch is also what makes the whitelist a compile-time fact, since adding a name to `SEMANTIC_TYPES` fails to build until `drawSemantic` handles it.
- **A path the user did not tick is structurally incapable of changing**, but the two layers are not the ones they look like. `validatePlan` runs when a blueprint is *designed*, not when one is loaded: `loadPlan` only re-parses the shape. What guards the serving path is `ai_plan_hash`, which covers `ai_fields`, so editing the field list makes the stored blueprint stale and it is dropped rather than run. The second layer is `setAtPath`, which only overwrites keys that already exist. Neither depends on the model behaving.
- **Every list the executor mirrors is tied to its source by a type, never by discipline.** `INSTANCES`, `LOCALE_COUNTRY` and `LOCALE_LABELS` are `Record<SupportedLocale, …>`; `drawSemantic` is a `switch` with no `default` returning a non-optional `JsonLeaf`, so a name added to `SEMANTIC_TYPES` fails to build until it is handled; and each `draw*` returns `EntityDrawOf<K>`, derived from `ENTITY_ATTRIBUTES` itself. That last one was the gap: `EntityDraw` is `Record<string, JsonLeaf>`, which matches anything, so `address.ward` and `address.district` were advertised to the model, accepted by `validatePlan` and then never drawn, leaving the field frozen with nothing logged. Both halves of the table are load bearing, since `validatePlan` clears a recipe by asking `entityAttributeType`, so a draw of the wrong type would write a string into a numeric field. `EntityDrawOf<K>` now makes a missing attribute and a wrong type both compile errors. The coverage test in `faker_entity.test.ts` stays as the runtime half: a type cannot see a draw that returns `undefined`.
- **Anything the DSL cannot express has to come back out.** `unapplied_hints` carries a dropped instruction; `unsupported_language` carries a language outside `SUPPORTED_LOCALES`, which `locale` cannot express because it is a closed enum. Without the second one a Thai body comes back with English names and nothing anywhere says why. Both are surfaced twice: in the preview panel, and on the endpoint list, since a blueprint built in the background is one the user never previewed.
- **Every recipe must produce the JSON type the body already holds**, checked against the real body in `validatePlan`. There are exactly two exceptions. `branch` may return `null` from an arm: an order that has not shipped needs `shipped_at` empty, not a date invented for it. And a field the body leaves `null` may be given any type, because `null` names no type to preserve, so the alternative was offering a checkbox that provably could not change anything. Widening it any further makes every response's shape unpredictable.
- **`ai_plan_hash` is the whole invalidation mechanism.** It covers the body (normalized through a parse, so whitespace does not count), the field list (sorted, so reordering checkboxes does not throw away a good blueprint) and the hint. Write paths no longer compare against the previous row: `PUT` just asks `isPlanStale` of the updated row. Any new write path that touches those three columns gets this for free, which is exactly why the comparison was moved off the routes.
- **The plan cache is keyed by the hash and confirmed against the text.** `ai_plan_hash` identifies the *inputs* a blueprint was built for, not the blueprint itself, so clearing a plan and rebuilding it from an unchanged body produces the same key twice. Comparing `source` is what stops a hit from handing back the previous blueprint forever. Anything added to `CachedPlan` has to be pure work on the blueprint alone, or a request would be served data derived from a different request.
- **Serving a fake request writes nothing at all.** `loadPlan` reads a column that came with the endpoint row, and `renderVariant` is pure. An endpoint with a blueprint schedules no `after()` work; only one whose blueprint is missing or stale does, and that work is a single build the next request benefits from. This is stronger than the old "serving only reads" rule and should stay that way.
- **`endpoints.ai_plan_started_at` is both the build lock and the retry cooldown.** It is released deliberately, not in a `finally`: only a build that stored a blueprint hands it back. A build that produced nothing leaves it set so the next request waits out `AI_PLAN_LOCK_MS` instead of hammering a dead provider. A quota refusal is the exception and hands the lock straight back: it reached no provider, so holding it would only delay the first legitimate build after the allowance resets. The timestamp is generated by the application, not `NOW()`, so both sides of the staleness comparison read the same clock, and the release carries it in its `WHERE` so a build that outran the lock cannot clear its successor's.
- **An edit ends the cooldown, so `clearPlan` drops the lock too.** The cooldown exists to stop a dead provider being hammered, and an edit is exactly the signal that the inputs changed. Without this a build that failed on a broken body kept the endpoint frozen for `AI_PLAN_LOCK_MS`, so the user fixed the body and the server went on quietly serving the base body.
- **Only an endpoint that actually serves variants is invalidated.** `isPlanStale` reports a blueprint as stale whenever `ai_enabled` is off or the field list is empty, because that is what `loadRenderable` answers, so `PUT` checks both flags *before* asking it. Asking it alone threw a good blueprint away on the edit that unticks Enable, and ticking it back on then charged a model call for a body that had not changed. The blueprint left behind can never be served or reported, since `resolveBody` and `loadRenderable` both refuse on the same two flags, and the row is picked up again unchanged the moment AI comes back on. The one thing this gives up is that an edit switching AI off no longer ends the cooldown, which costs nothing while nothing wants a blueprint.
- **A build re-checks that it still owns its lock before it writes.** A model call takes seconds and an edit can land in the middle of one: `clearPlan` wipes the blueprint and drops the lock, and the build still in flight would otherwise store a blueprint for a body that no longer exists.
- **The lock and the blueprint are written with `$executeRaw`, on purpose.** `endpoints.updated_at` carries `@updatedAt`, and Prisma stamps it on every write it generates with no per-query opt out. Blueprint work is machine work the user never asked for, so it must not reorder the `updated_at desc` endpoint list they are looking at. Routing no longer depends on that ordering, but the list still does.
- **A rejected blueprint gets exactly one repair attempt, carrying the reasons back.** There is no structured-output schema on the plan call: the DSL is a deep discriminated union that providers refuse about as often as they accept, and Zod plus `validatePlan` is the real gate either way. One repair is affordable because designing is rare; a loop would not be.
- **The daily quota counts model calls, in `ai_usage_logs`.** It used to count rows in `endpoint_ai_variants`, so a preview slipped past it entirely and a create/delete loop refunded it. Every path that reaches `buildPlan` has to claim its call with `trySpend` **before** the call, and there are exactly two: `ensurePlan` and the preview route. `adoptPlan` is the third way to a stored blueprint and deliberately not a third meter: it reaches no provider, so it takes no quota and no lock. What it must never skip is `validatePlan`, since a hash alone only says the blueprint was built for these inputs. One transaction rather than a check then an insert, because two concurrent builds would otherwise both pass the same check. Recording after the call meant a design that failed spent up to two provider calls and charged nothing, which is backwards: what the quota protects is the bill, not the number of blueprints that came out.
- **faker is loaded lazily on the serving path, and never through a computed specifier.** The fake-API route reaches the executor with `await import("…variant/faker.service")` past both AI guards, so an endpoint with no blueprint never pays for eight locale datasets. The specifier is a literal because a computed one (`…/locale/${plan.locale}`) cannot be traced by the bundler and would go missing on a standalone deploy, quite apart from letting an untrusted `locale` pick a module. The locale instances stay statically imported for the same reason.
- **`renderVariant` is synchronous and has to stay that way.** The eight Faker instances are module-scope singletons shared by every request, and only a function with no `await` in its body cannot interleave two renders on the same PRNG. This is the real cost of ever making the executor async.
- **Rendering more samples is free and must stay free.** The preview route only meters the design half. A blueprint reaches the free path two ways: the caller sends one with the hash it was built for, or the caller names an endpoint and the route reads that row's own `ai_plan` through `planForHash`. Both are judged by the same pair, and when it passes the route renders and returns without touching a model, a quota or a cooldown. The hash decides *whether it describes these inputs*; `validatePlan` decides whether it is safe. Never let the hash alone stand in for validation.
- **The blueprint never travels with an endpoint list.** It is up to `MAX_PLAN_BYTES` per row and a list carries every row, so `EndpointInfoSchema` exposes `ai_has_plan` instead: one boolean saying a usable blueprint exists, derived from the `planInfoOf` the route already asks for. That is enough for the update form to offer a free reroll, and the blueprint itself only moves when a preview asks for it by naming the endpoint. This is also why the endpoint that stores a blueprint must be read with `getEndpointInGroup` rather than by id: the caller was cleared for one group.
- **An array container path is a length, not a value.** Ticking `items` means "return a different number of elements"; ticking `items[].price` means "vary the contents". `splitSelection` separates them, and `array_length` runs before every other recipe in that array so entities and catalogs are drawn once per element of the new length. The extra elements are cloned from element zero, which is why an empty array cannot have its length varied. A clone also carries element zero's value for every path that was *not* ticked, so a list whose length varies but whose `id` was left out comes back with the same id on every extra item. That is correct behaviour and the executor must not paper over it, so `AiFieldSelector` says it on the row instead: the only real fix is ticking the field.
- **A reference reads one element, at the indices being drawn.** A `copy`, `after`, `product`, `template` ref or `branch` `on` pointing into an array the field is not part of resolves to `undefined` and leaves the field frozen at its base value with nothing logged. `validatePlan` compares `scopeKeyOf` of the field against `scopeKeyOf` of each dependency, where a scope is the innermost array a path sits in: an outer scope is readable from an inner one, the reverse is not, and a different array is not. `sum` is the single exception, since it reads a whole array through `flattenPathValues` rather than one element, and `wholeArrayReads` is what carves it out. Any recipe added later that reads a whole array has to be added there too.
- **An entity or catalog is drawn once per scope, so every path bound to it must sit in one.** `validateScopes` refuses a blueprint that uses one id both inside and outside an array, or in two different arrays. Without it the cache key (`id` plus the index path) would quietly link `users[0]` to `orders[0]`, which is one draw and many draws asked for at the same time.
- **A path is a length when everything it resolves to is an array.** `items` and `rows[].cells` are both lengths, and one `array_length` recipe resizes every array the second one names, cloning each array's *own* first element. `splitSelection` decides this by looking at the values, not by looking for `[]` in the text, because `rows[].cells` has a marker and is still a length while `grid[]` has one and is also a length.
- **`ctx.indexes` is a path of indices, outermost first.** A field two arrays deep is drawn once per element of every inner array, and `readReferenced` walks a dependency down as many levels as that dependency itself crosses. `validatePlan` is what makes those indices the right ones: `isOuterScope` allows a dependency in the same array or in one wrapping it, so the field's own indices always cover it. The entity and catalog cache keys carry the whole index path, or one draw would be shared across an entire inner array.
- **`unique` is one set per field, not per innermost array.** An id drawn across `rows[].cells[]` has to be unique over every cell in the response, since that is what a reader of the response sees.
- **A field list that is empty and one that was emptied are different failures.** `buildPlan` answers `NO_FIELDS_SELECTED` only when nothing was selected; a list that arrived non-empty and lost every path answers `FIELDS_NOT_PATCHABLE`. They shared a message, so a user who had ticked several boxes and then edited the body out from under them was told to tick at least one.
- **`unapplied_hints` is not decoration.** A hint the DSL cannot express is the one failure a user has no other signal for: they type a request, the data ignores it, and nothing says whether the model misread it or the feature cannot do it. The prompt requires the dropped part to be quoted back, and the UI shows it.
- **The blueprint's one weakness is that a misread field stays misread**, where a per-call model would only get it wrong sometimes. That is what the preview summary and the Redesign button are for, and why the hint is documented as outranking anything inferred from field names. Anything that hides the summary takes away the only repair path a user has.
- **A length is not capped at `MAX_ARRAY_ITEMS`, a value is.** `resizeArrays` reads its path uncapped while `renderField` reads its own capped, and the difference is deliberate: a length describes the whole array, so a grandfathered row longer than the cap still gets every one of its nested arrays resized, while the values inside it are only varied for the first `MAX_ARRAY_ITEMS` elements, which is exactly what `AiFieldSelector` promises on the row. Every other `getAtPath` on a path that can cross an array passes the cap.
- **`endpoints.ai_plan_at` is written and never read.** It records when a blueprint was stored, for looking at a row by hand. Nothing branches on it, `ai_plan_hash` is what decides staleness, and adding a read would quietly make it a second source of truth.
